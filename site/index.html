Three genomics tools rebuilt in DuckDB SQL, checked against the originals

duckseq rebuilds hand-written genomics tools from three parts: standard formats such as Parquet, DuckDB SQL over DuckHTS readers, and, where SQL alone is not enough, a small native kernel. Each demo reports exact comparisons, measurements, and where its evidence stops.

The same step is a few lines of SQL

Reading, joining and writing are ordinary SQL statements. These excerpts are copied unchanged from the repository, so each one is also something you can run.

The join key is ID, REF and ALT together, so two alleles at one position stay distinct. LDZip aborts on duplicate IDs such as CHROM:POS; this build accepts them.

What you can run

Each demo has a command you can run from a clone of the repository. Only peakwhere runs without a toolchain, because it is a web page.

peakwhere

In a browser, on this site. Files stay on your computer and the page makes no requests outside its own origin. To serve it locally:

cd demos/peakwhere
npm ci
npm run stage && npm run stage:peek && npm run vendor
npm run serve
npm test

AIE

Builds the pinned Gravlax oracle with Cargo, then replays the fixture. Needs Rust, R, samtools, jq, curl and unzip.

cd demos/aie
./setup.sh
./test.sh
./mutation_test.sh

LDZip

The small fixture check needs R, a C++ toolchain, make, curl and unzip. The full chr20 benchmark is separate.

cd demos/ldzip
./setup.sh --no-data
./test.sh

# full chr20 benchmark
./full_test.sh
./measure_build.sh
./measure_queries.sh

Three demos, three different amounts of evidence

The demos are at different stages. What each page below claims is limited to what its report verified.

peakwhere

Original
peakwhere and PeakPeek (Sean Davis); ChIPseeker only as the timing comparison
Question
Where do ChIP-seq peaks fall relative to genes?
Scope
W1: 7,220 mouse thymus chr19 peaks in five files against GENCODE M25 basic chr19

The SQL reproduces the independent base-R oracle on W1 exactly, with zero unmatched peaks. Native DuckDB took 0.401 s on one thread and 0.370 s multithreaded, against 2.776 s for ChIPseeker’s annotatePeak, and used less memory.

DuckDB SQL ChIPseeker. Wasm peak memory was not measured.

This is not an equal-output speedup. ChIPseeker also finds the nearest transcript and uses different category rules. On W1 the two differ in all six category totals, most of all in promoters (2,176 in SQL, 1,266 in ChIPseeker); the report compares marginal counts and does not decompose why. Timings cover the two analysis phases, not startup. Including process startup, the native runs take 0.454 s and 0.431 s and ChIPseeker 8.289 s.

Where the original wins

On the larger W2 workload (221,308 peaks, full GENCODE M25 and ENCODE files), native DuckDB is still faster (9.699 s and 7.395 s against 25.782 s) but uses more memory: 3,297 MiB and 4,903 MiB against ChIPseeker’s 2,143 MiB. The W2 oracle timed out at 120 s, so W2 has no independent count check; only the three SQL engines agree with each other.

AIE

Original
Gravlax aie 0.2.3, built from a pinned commit
Question
Can BAM evidence become Parquet relations whose SQL counts match Gravlax?
Scope
The checked-in synthetic fixture, two samples, two annotation versions
Exactregion, junction, jset and annotation-replay counts match Gravlax for both samples
7mutation checks, each of which fails when an annotation rule is altered
Noneperformance benchmarks have been run

The fixture was written to separate rules that a naive query would blur: UMI chains versus ties, multimappers that span genes versus ones confined to one, and a read that supports two junction predicates at once.

Scope limit. The fixture uses twelve-base ACGT UMIs. Gravlax orders packed numeric keys and SQL orders text; they agree for equal-length UMIs, but UMIs of differing lengths with leading A bases have not been tested. This is not parity over all Gravlax input modes, and the fixture is not performance evidence.

LDZip

Original
LDZip and LDZipMatrix, commit f8e363a
Question
Can one SQL file build an equivalent LD matrix and allele-aware variant keys in Parquet?
Scope
Nested chr20 tutorial regions from 20,000,000 bp: 250 kb, 500 kb and 1 Mb (5,764, 11,590 and 22,833 variants), 503 EUR samples
Exact8-bit and 16-bit matrices at all three region sizes, against LDZip decode
6mutation checks, including an ID-only join that returns 1,170,740 rows instead of 678,614 at 1×
171CHROM:POS IDs collide in the 1× region; LDZip aborts on them and the SQL build accepts them

The comparison queries Parquet through DuckDB. It includes no compressed LDZip reader built on DuckDB, and no claim that Parquet replaces LDZip’s general pipeline. Each build and query cell ran in three fresh processes, within budgets declared beforehand: 300 s wall time, 16 GiB peak RSS and 10 GiB temporary output.

DuckDB SQL LDZip. The DBI path returns a dense R matrix, as LDZipMatrix does.

LDZip wins these. It returns the dense 5,000-variant matrix faster and with less memory, and the SQL build uses 20 to 35 times its peak memory. It also stores a smaller 16-bit matrix (6,406,716 B against 8,023,822 B at 4×). The SQL build is slower at 1×, level at 2× and faster at 4× (0.57 s against 0.79 s).

Its Parquet variant table is about 15 times smaller than LDZip’s text and SQLite index. The pair-speed comparison needs a fair rerun: LDZip requests are grouped along the wrong axis, and SQL returns encoded nullable values rather than decoded zero-filled correlations. Tag timings compare a SQL batch with 100 LDZip API calls. The regions are nested spans, not exact 1×/2×/4× row scaling, and the full chr20 matrix was not built.

Native execution has an output cost. In the separate 5,000-variant/16-bit experiment, TinyCC exporting and retaining SQL matrix lists takes 1,039 ms (one thread) or 734 ms (four); LDZip’s R matrix takes 109 ms. Direct C-buffer consumption takes 103/39.5 ms but returns checksums, not a retained matrix. Built-in dense-grid SQL fails its 1 GiB buffer limit. BLAS linkage is verified; GEMM performance is unmeasured.

Four standards every demo is held to

A demo is complete only when it has all four. The ledger below shows which demos do.

Upstream parity

The same answers on the original tool’s own test data or tutorial, compared exactly rather than approximately.

Mutation checks

Each rule is deliberately implemented wrongly, and the comparison has to fail.

Measured performance

Under DuckHTS STYLE.md: 1×, 2× and 4× inputs, three fresh processes, peak RSS, and budgets declared before measuring.

Contrast with the original

A table that includes the cases where the original tool is faster, leaner or smaller.

Where the evidence is incomplete

  • No demo has shown a general speed or memory advantage. Each result belongs to its fixture, region set and machine (one Intel Core i5-13500 host in the LDZip and peakwhere reports).
  • peakwhere has no mutation checks reported and no 1×/2×/4× scaling. Its W2 independent oracle timed out, so W2 is cross-checked only among the SQL engines. ChIPseeker applies different rules, so its timing is not an equal-output speedup.
  • AIE has no performance measurement and no contrast table. Parity is for one synthetic fixture with equal-length UMIs; other Gravlax input modes are untested.
  • LDZip covers three nested chr20 spans. The full-chromosome matrix was not built, so its cost is unknown. Pair batching and output semantics need a fair rerun; the review identifies an avoidable 200 MB dense-matrix copy and comparator gaps. The report does not claim equivalent indexes or a compressed LDZip reader built on DuckDB.
  • Reproduction. Receipts for peakwhere are in its results.json. The AIE and LDZip scripts regenerate their derived data from checked-in fixtures or checksummed inputs.
